\# Feature Dictionary



\## 1. Purpose



This document defines the features used in the user purchase prediction task.



The modeling unit is a user-item pair (`user\_id`, `item\_id`).



The prediction task is:



> Use historical user-item interaction information to predict whether the user

> will purchase the item during a future label window.



To reduce data leakage, all model features are calculated only from the feature

window. Future purchase information is used only to construct the target label.



\---



\## 2. Time-window design



\### Training dataset



Feature window:



\- 2025-11-18 00:00:00

\- to 2025-12-03 23:59:59



Label window:



\- 2025-12-04 00:00:00

\- to 2025-12-10 23:59:59



\### Validation dataset



Feature window:



\- 2025-11-18 00:00:00

\- to 2025-12-10 23:59:59



Label window:



\- 2025-12-11 00:00:00

\- to 2025-12-18 23:59:59



The model is therefore trained using an earlier period and evaluated using a

later period rather than a random train-test split.



\---



\## 3. Candidate-generation rule



The modeling dataset does not use every possible user-item combination.



Candidates come from two sources:



1\. Historical user-item pairs

2\. Top-10 popular items from categories previously interacted with by the user



The Top-10 setting was selected after comparing Top-5, Top-10 and Top-20

candidate-generation strategies.



Candidate coverage results:



| Candidate strategy | Future purchase coverage |

| --- | ---: |

| Historical only | 22.98% |

| Category Top-5 | 23.91% |

| Category Top-10 | 24.50% |

| Category Top-20 | 25.21% |



Top-10 was selected as a compromise between candidate-set size and purchase

coverage.



\---



\## 4. Feature dictionary



| Feature | Type | Definition | Calculation logic | Preprocessing | Interpretation |

| --- | --- | --- | --- | --- | --- |

| `total\_behaviors` | Numeric | Total number of historical interactions between a user and an item | `COUNT(\*)` grouped by `user\_id, item\_id` inside the feature window | Missing values are filled with 0 for recalled items without direct historical interaction; standardized for Logistic Regression | Measures overall user-item interaction intensity |

| `view\_count` | Numeric | Number of historical view behaviors for a user-item pair | Count rows where `behavior\_type = 1` | Missing values filled with 0; standardized for Logistic Regression | Measures browsing activity for the item |

| `favorite\_count` | Numeric | Number of historical favorite behaviors | Count rows where `behavior\_type = 2` | Missing values filled with 0; standardized for Logistic Regression | Represents an explicit interest signal |

| `cart\_count` | Numeric | Number of historical add-to-cart behaviors | Count rows where `behavior\_type = 3` | Missing values filled with 0; standardized for Logistic Regression | Represents relatively strong purchase intention |

| `active\_days` | Numeric | Number of distinct dates on which the user interacted with the item | `COUNT(DISTINCT DATE(timestamp))` | Missing values filled with 0; standardized for Logistic Regression | Measures persistence of user interest across multiple days |

| `days\_since\_last\_behavior` | Numeric | Number of days between the feature-window cutoff and the most recent user-item interaction | `julianday(feature\_end) - julianday(MAX(timestamp))` | Historical pairs use calculated value; recalled items without direct history use `-1`; standardized for Logistic Regression | Measures recency of user interest |

| `seen\_historically` | Binary | Whether the exact user-item pair appeared during the feature window | 1 if the pair exists in historical interactions, otherwise 0 | Kept as 0/1 | Distinguishes previously interacted items from newly recalled candidate items |

| `from\_category\_recall` | Binary | Whether the item was recalled through the user's historical category interests and the category Top-10 popularity rule | 1 if candidate appears in category recall table, otherwise 0 | Kept as 0/1 | Indicates whether the candidate was generated by category-based recall |

| `label\_purchase` | Binary target | Whether the user purchased the candidate item during the future label window | 1 if `behavior\_type = 4` occurs for the user-item pair during the label window, otherwise 0 | Used only as prediction target; never used as an input feature | Target variable for purchase prediction |



\---



\## 5. Identifier fields



The following fields are retained for identification and recommendation output,

but are not directly used as numeric model features.



| Field | Meaning | Model treatment |

| --- | --- | --- |

| `user\_id` | Unique user identifier | Not used as a direct numeric feature |

| `item\_id` | Unique item identifier | Not used as a direct numeric feature |



The identifiers are excluded because their numeric values do not have a

meaningful continuous relationship with purchase probability.



\---



\## 6. Missing-value treatment



Candidate generation introduces items that may not have direct historical

user-item interaction records.



For these category-recalled candidates:



\- `total\_behaviors = 0`

\- `view\_count = 0`

\- `favorite\_count = 0`

\- `cart\_count = 0`

\- `active\_days = 0`

\- `days\_since\_last\_behavior = -1`

\- `seen\_historically = 0`



This allows newly recalled candidates to remain in the modeling dataset instead

of being removed because historical pair-level features are unavailable.



\---



\## 7. Leakage prevention



Future purchase behavior must not be used as an input feature.



For this reason, variables such as:



\- future purchase count

\- future purchase time

\- future conversion information



are not included in model features.



`label\_purchase` is generated only from the future label window.



The feature window always ends before the corresponding label window starts.



\---



\## 8. Feature discrimination assessment



Initial feature discrimination was examined through the standardized

coefficients of the Logistic Regression baseline.



The coefficients were:



| Feature | Standardized Logistic coefficient |

| --- | ---: |

| `seen\_historically` | 1.7790 |

| `total\_behaviors` | 1.7391 |

| `view\_count` | -1.1582 |

| `days\_since\_last\_behavior` | -0.7742 |

| `cart\_count` | 0.2255 |

| `from\_category\_recall` | 0.2005 |

| `active\_days` | -0.1434 |

| `favorite\_count` | 0.0295 |



The largest coefficient magnitudes were observed for:



\- `seen\_historically`

\- `total\_behaviors`

\- `view\_count`

\- `days\_since\_last\_behavior`



This suggests that historical user-item exposure, interaction intensity and

interaction recency contain useful predictive information.



However, coefficient signs should not be interpreted independently as causal

effects.



For example, `view\_count` has a negative coefficient while

`total\_behaviors` has a positive coefficient. These variables are strongly

related because views form a large part of total interactions. Therefore the

negative coefficient does not mean that more browsing directly reduces

purchase probability. It should instead be interpreted conditionally with the

other behavior-count variables held constant.



A separate feature-effectiveness report will further examine:



\- feature correlations

\- correlation heatmap

\- feature importance

\- feature ranking

\- differences between purchased and non-purchased samples

\## 9. Model evidence



Two models were evaluated using the same temporal validation dataset.



| Metric | Logistic Regression | HistGradientBoosting |

| --- | ---: | ---: |

| ROC-AUC | 0.9203 | 0.9281 |

| PR-AUC | 0.032219 | 0.049415 |

| PR-AUC lift over random | 37.77x | 57.93x |

| Precision @ 0.5 | 0.0455 | 0.0504 |

| Recall @ 0.5 | 0.3181 | 0.4340 |

| F1 @ 0.5 | 0.0796 | 0.0903 |



The improved performance of HistGradientBoosting suggests that nonlinear

interactions between the engineered features contain additional predictive

information beyond the linear baseline.



\---



\## 10. Current limitations



The feature set is intentionally compact and currently focuses mainly on

user-item interaction history.



Important limitations include:



1\. Candidate coverage is only 24.50% using the selected Top-10 category recall

&#x20;  strategy.

2\. No richer item-level popularity, category preference intensity or user-level

&#x20;  behavioral profile features are currently included in the final model.

3\. The validation period contains a strong activity and purchase peak on

&#x20;  2025-12-12, so performance may differ between normal and high-activity

&#x20;  periods.

4\. Because negative samples were downsampled during training, model output

&#x20;  scores should mainly be interpreted as ranking scores rather than calibrated

&#x20;  real-world purchase probabilities.
